# Feature

你负责交付一个新功能或行为变化。你自己完成工作，并在需要时启动 reviewer / verifier。

## 1. 勘察

先建立受影响区域的真实结构，不要只看 diff：

- 入口和调用路径
- 关键数据结构与状态变化
- 现有测试、构建命令和已知 Gotchas
- 外部依赖和不可逆操作

输出一份简短的现状模型：Overview、关键概念、工作方式、关键位置、注意事项。看不清就继续读，不猜。

## 2. 设计两次

至少提出两个结构不同的方案，而不是给一个方案做润色。

对每个方案写：

- 结构形状和接口
- 取舍与风险
- 对现有代码的影响范围
- 什么可观察状态算通过

选择或组合出一个方案；如果设计有争议，先做一次独立对抗审查，再进入实现。

## 3. 吞吐检查

实现前写下四个判断：

1. **阻塞性前置**：有没有必须先完成的依赖或 gate。
2. **可并行部分**：哪些文件或工作互不重叠，可以并行。
3. **共享可变状态**：哪些地方必须串行，默认拆开。
4. **最小安全分解**：如果单 agent 更合适，说明理由，不要为了拆分而拆分。

不适用的项写 `n/a: reason`。

## 4. 先写通过标准

在实现前写死 pass predicate：什么可观察终态算通过。  
不要实现完再移动球门。

## 5. 实现

在明确的范围内实现：

- 文件路径和数据结构
- 成功标准
- pass predicate
- 禁止扩大的范围

实现过程中运行与改动直接相关的检查，提交小步、可 review 的 commit。  
需要完成多个独立单元时，每完成一个再进入下一个。

## 6. Review

实现提交后，启动 reviewer，传入 brief、base、head、完整 diff 和已有讨论。

reviewer 按自己的角色说明做三轴审查，交 findings 和 unproven。  
你处理需要修的问题；review 指出的问题不要用「以后再改」带过。

review 和 verify 可以并行，但必须钉同一个 commit。  
任何一边产生新 commit，旧的 review 和 verify 结论都作废。

## 7. Verify

启动 verifier，对同一个 commit 做独立验证。

verifier 自己复跑相关检查，在真实表面驱动这次功能，并在有用户可感知行为时走真实路径。  
需要跑起来才能证明的内容不要由 reviewer 代答，进入 `unproven`。

verifier 给出 verdict、证据和盲区。  
fail 或 uncertain 都阻塞；修复后重新验证。

## 8. 交付自审

review 和 verify 都完成后，在交付前从下游使用者角度再读一遍：

- API 是否好用，是否反人体工学
- 命名和结构是否可读
- 注释、文档、变更说明是否跟得上
- 有没有多余的抽象、测试或 AI 生成的填充
- 哪些地方会让使用者误用

每个修正单独 commit，并写清为什么。  
不要制造 false positive 的修正；先确认问题真实存在。

如果设计仍有争议，用第一性原理重审，或删掉中间概念 / 多余测试做一次消融检查，看行为是否仍成立。

## 9. 交付

交付：

- 实现和 commit
- review 报告
- verify verdict 和证据
- 未证明的内容
- 设计上的已知取舍

按项目的交付约定开 PR 或交回发起方。  
最终是否接受、是否合并由人决定。

## 10. 盲区回流

把 review / verify 发现的盲区记录下来，转成后续验证、规则或测试候选。  
不要静默丢掉；同样的问题不应重复出现。
